Coordinate corrections (this server's hotels.csv)

Upload a reviewed coordinate_changes.csv from scripts/coordinate_audit.py. Only rows marked "auto" or "yes" are applied, and only their latitude and longitude. The file is backed up first, checked after writing, and every change is logged. Rows already applied are skipped, so applying twice is safe.

Google IDs found by a lookup run elsewhere (google_ids_upload.json), so they are not paid for again. IDs this server already has are kept; nothing is overwritten.

Approve candidates: a coordinate_candidates.csv from scripts/find_candidates.py with approve = "yes" on the rows you checked (one per hotel). Each approved row sets that hotel's Google ID and moves its coordinates to Google's position. Other rows are ignored. Both files are backed up first; approving twice is safe.

Change the hotel list: a CSV with the columns hotel_id and action, optionally hotel (the current name, checked against this server's list) and reason. Actions: hide, unhide, remove, rename (new_name), city (new_city, optionally new_region), owner (new_owner), rooms (new_rooms: the room count, a whole number), brand (new_brand, new_brand_group), notes (new_notes), merge (removes a duplicate: into = the id of the hotel kept; saved comp sets switch to the kept hotel), add (a new hotel: hotel_id = its new id, hotel = its name, and new_city, new_region, new_category, new_brand, new_brand_group, new_keys, new_year_opened, new_status, new_lat, new_lng, new_owner and the other hotels.csv columns as new_…; perf_… columns add its performance.csv row; refused if the id or the name is taken or on the do-not-add list), to_pipeline (moves the hotel to the pipeline: new_name, pipeline_status, expected_opening, or pipeline_id to rename an existing project instead), pipeline_add (a project not open yet: pipeline_id, hotel = its name, new_city, new_region, new_category, new_brand, new_brand_group, new_owner, new_keys, new_expected_opening, new_status, new_investment_mad, new_lat, new_lng, new_notes; refused if the id or the name is taken), pipeline_position (pipeline_id, hotel = the project's name, new_lat, new_lng, approximate=yes if it is a town-centre estimate). Hidden hotels keep their row but are left out of every page, count, KPI and scraper run; remove deletes the row. hotels.csv and pipeline.csv are backed up first; running the same file twice changes nothing; restore a backup below to undo.

Owner profiles: an owners_upload.json ({"format": "kodo-owners-1", "owners": [...]}) adds an owner profile, or replaces the one with the same id. Owners not in the file are kept as they are. owners.json is backed up first; applying twice changes nothing; restore a backup below to undo.

Occupancy Model

Modelled occupancy: price coverage of the stored nights and the last model run. Price coverage describes how many recent published prices we have, not how accurate the estimate is. Model shown on the platform: — (environment variable OCC_MODEL).

Calibration runs once a month, after the first model run of the month, against the real figures in daily_performance.csv (Upload performance). It reports the average error of v1 and v2 by city and hotel type in the Rates panel; with no real figures it does nothing and says so.

Events

The events database behind the Tourism calendar, the calendar markers and the occupancy model. The base list (events.json) ships with the code; changes made here are saved on this server (event_overrides.json), survive deploys and are logged. Hiding an event removes it from every page and from the model; showing it again puts it back.
